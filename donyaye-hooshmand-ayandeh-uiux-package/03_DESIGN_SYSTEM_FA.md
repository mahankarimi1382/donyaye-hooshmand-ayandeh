# Design System — دنیای هوشمند آینده

> این مشخصات یک نقطه شروع بصری است. لوگو یا brand guide واقعی، اگر پیدا شد، مرجع نهایی رنگ و هویت است. هیچ رنگ/فونتی نباید در همه فایل‌ها به‌صورت پراکنده هاردکد شود.

## 1. جهت بصری: «اعتماد صنعتی + دقت کشاورزی/تغذیه»
تصویر کلی: حرفه‌ای و مشخص، علمی، روشن، مرتب و ملموس. از المان‌های استعاریِ غلات، بافت ماده خام یا ساختار شبکه زنجیره تأمین با ظرافت استفاده کن؛ تصویر شلوغ با چند آیکون گیاه و پس‌زمینه سبز ژنریک نساز. فضای سفید کافی، کنتراست بالا، سطح‌بندی روشن و تیترهای کوتاه باید توجه را به محصول و اقدام اصلی هدایت کند.

## 2. پالت پیشنهادی اولیه
ابتدا رنگ برند واقعی را بررسی کن. در نبود brand guide، این پالت را به‌عنوان prototype ثبت و پس از تست contrast اصلاح کن:

| Token | مقدار پیشنهادی | کاربرد |
|---|---|---|
| `--color-forest-950` | `#102820` | متن/بخش‌های عمیق و footer |
| `--color-forest-800` | `#1B4332` | رنگ برند پایه/هدر/لینک مهم |
| `--color-leaf-600` | `#3D7855` | اقدام اصلی یا accent کنترل‌شده |
| `--color-grain-500` | `#C99A3A` | accent کوچک و هایلایت؛ نه متن ریز روی سفید |
| `--color-cream-50` | `#FAF8F1` | پس‌زمینه گرم |
| `--color-surface` | `#FFFFFF` | سطح کارت و فرم |
| `--color-ink-900` | `#17211C` | متن اصلی |
| `--color-ink-600` | `#52635A` | متن ثانویه |
| `--color-border` | `#DDE5DE` | خط مرزی و divider |
| `--color-success` | بر اساس palette معنایی با contrast تست‌شده | موفقیت |
| `--color-warning` | بر اساس palette معنایی با contrast تست‌شده | هشدار |
| `--color-danger` | بر اساس palette معنایی با contrast تست‌شده | خطا |

قواعد:
- رنگ semantic را از رنگ brand جدا نگه دار؛ رنگ موفقیت/خطا فقط برای تزئین برند استفاده نشود.
- برای متن معمولی، نسبت کنتراست حداقل 4.5:1 هدف‌گذاری شود؛ برای متن بزرگ حداقل 3:1 طبق WCAG AA.
- رنگ به‌تنهایی حامل معنا نباشد؛ آیکون/متن و state هم نمایش داده شود.
- پالت در یک فایل central tokens تعریف شود و بعد از آن در تمام componentها مصرف شود.

## 3. تایپوگرافی
- فونت فارسی باید واضح و دارای مجوز استفاده تجاری مناسب باشد. `Vazirmatn` می‌تواند نامزد اولیه باشد؛ انتخاب نهایی باید از نظر مجوز، شکل اعداد، نیم‌فاصله، وزن‌ها و عملکرد در دستگاه‌های هدف بررسی شود.
- یک خانواده اصلی برای متن و ترجیحاً یک خانواده مکمل/وزن display در صورت توجیه طراحی انتخاب کن؛ نه چند فونت نامرتبط.
- از فونت‌های سنگین یا چند وزن بلااستفاده دانلود نکن؛ subset یا `unicode-range` را فقط اگر pipeline پروژه پشتیبانی و تست می‌کند استفاده کن.
- سطح‌های پیشنهادی دسکتاپ/موبایل به صورت fluid:
  - Display: `clamp(2.2rem, 4.2vw, 4.5rem)`؛ line-height حدود 1.15–1.3
  - H1: `clamp(2rem, 3.5vw, 3.5rem)`
  - H2: `clamp(1.55rem, 2.5vw, 2.4rem)`
  - H3: `1.25–1.6rem`
  - Body large: `1.0625–1.125rem`
  - Body: `1rem` یا بزرگ‌تر اگر خوانایی بهتر شود
  - Meta: معمولاً کمتر از `0.875rem` نشود مگر اطلاعات واقعاً ثانویه و قابل دسترس باشند.
- line-height فارسی متن اصلی عموماً 1.7–1.95 را تست کن. تیترها و متن جدول می‌توانند متفاوت باشند.
- از کشیده‌سازی مصنوعی متن، سطرهای بسیار عریض و justified text برای متن فارسی اجتناب کن.

## 4. Grid و spacing
- پایه spacing: 4 یا 8 پیکسل، با توکن‌های مرکزی.
- عرض متن مقاله محدود و خوانا؛ صفحه کاتالوگ و grid محصول می‌تواند پهن‌تر باشد.
- grid دسکتاپ متناسب با breakpointهای stack فعلی؛ نقطه شروع: 12 ستون با max-width حدود 1200–1320px.
- موبایل اول: padding افقی واقعی معمولاً 16–20px؛ breakpointها بر اساس محتوا و تست، نه صرفاً اعداد رایج.
- section spacing باید به hierarchy صفحه کمک کند؛ همه بخش‌ها فاصله عمودی یکسان و بی‌معنا نداشته باشند.
- کارت‌ها فقط در جایی استفاده شوند که محتوا entity یا action مشخصی دارد. از تبدیل همه متن‌ها به card پرهیز کن.

## 5. RTL و locale
- `dir="rtl"` باید از سطح سند یا layout زبان اعمال شود.
- از `start/end` و CSS logical properties بهره ببر؛ جهت آیکون‌های back/forward، breadcrumb، carousel و pagination باید در RTL بازبینی شود.
- ایمیل، URL، کد محصول و رشته‌های لاتین را در متن راست‌چین با `dir="ltr"` یا bidi isolation درست نمایش بده.
- از اتصال رشته فارسی با قطعات ترجمه hard-code شده اجتناب کن؛ برای زبان دوم از i18n موجود استفاده کن.
- حروف‌چینی فارسی: نیم‌فاصله، ی/ک فارسی، علامت‌گذاری و اعداد با قاعده واحد. شناسه محصول/شماره تماس را ناخواسته به ارقام فارسی یا برعکس تبدیل نکن اگر ارتباط با سیستم‌های دیگر مهم است.
- فرم‌ها، dropdownها، date picker، file upload، toast، modal و focus trap را در RTL به صورت واقعی تست کن؛ صرف تغییر `direction` کافی نیست.

## 6. Shape و elevation
- گوشه‌ها متناسب با هویت: کوچک و متعادل؛ از گردی افراطی که تجربه را شبیه یک قالب generic می‌کند پرهیز کن.
- shadow باید subtle و معنی‌دار باشد؛ border و contrast اغلب از shadowهای بزرگ بهترند.
- سطح‌های اصلی: page background، surface، elevated surface، overlay. تعداد لایه‌ها محدود باشد.
- کارت محصول باید تصویر/نام/داده کلیدی/CTA را در ترتیب یکسان و با ارتفاع قابل کنترل داشته باشد.

## 7. کامپوننت‌های پایه
- Button: primary، secondary، tertiary/ghost، destructive، link؛ اندازه‌های sm/md/lg؛ loading و disabled واقعی.
- Link: با ظاهر قابل تشخیص از متن معمولی و focus visible.
- Input/Textarea/Select/Combobox: label همیشه قابل مشاهده، helper/error text، `aria-describedby`، disabled/loading.
- Search field: clear action، keyboard support، empty state.
- Product card، Category card، Product spec table، Document link، Quote/Inquiry form، Breadcrumb، Pagination، Accordion، Tabs فقط در صورت کاربرد، Modal/Drawer، Toast، Skeleton، Empty state، Error state، Alert، Badge status.
- Header، Mobile navigation، Footer، Section heading، CTA band و page container.
- کامپوننت‌های data display باید long text، مقدار ناموجود، واحدها و حالت mobile را پشتیبانی کنند.

## 8. انیمیشن و motion
- transitionهای کوتاه و عملکردی، اغلب 150–250ms؛ از مدت‌زمان‌ها و easingهای متنوع و بی‌دلیل خودداری کن.
- hover نباید تنها راه فهم وضعیت یا تعامل باشد.
- هیچ محتوای اصلی نباید به انیمیشن ورود وابسته باشد تا دیده شود.
- `prefers-reduced-motion: reduce` را پشتیبانی کن.
- از scroll hijacking، parallax سنگین، cursor سفارشی مزاحم و انیمیشن‌های طولانی در مسیر فرم B2B اجتناب کن.
- motion library فقط در صورت نیاز واقعی و پشتیبانی stack نصب شود.

## 9. عکس، تصویر و آیکون
- تصویر واقعی از محصول/مواد اولیه/بسته‌بندی/تجهیزات فقط در صورت ارتباط با شرکت و اجازه انتشار استفاده شود.
- اگر عکس واقعی نداریم، تصاویر editorial با مجوز روشن یا artwork انتزاعی هدفمند به‌کار ببر؛ به تصویر عمومی یک ماده یا کارخانه برچسب محصول شرکت نزن.
- alt باید هدف تصویر را توصیف کند و برای تصویر تزئینی `alt=""` باشد.
- آیکون‌ها از یک خانواده واحد مانند Lucide یا خانواده سازگار با stack انتخاب شوند؛ emoji جایگزین آیکون UI نشود.
- تصویر hero فشرده و responsive؛ ابعاد در HTML معلوم؛ استفاده از background-image برای تصاویر محتوایی مهم اجتناب شود.

## 10. حالت‌ها و feedback
برای هر کامپوننت تعاملی، حالت‌های default، hover، active، focus-visible، disabled، loading، error و success را که معنادارند تعریف کن. دسترس‌پذیری صفحه‌کلید و focus order باید در طراحی لحاظ شود، نه اینکه بعداً اضافه شود.

## 11. مستندسازی و نگهداری
- Design tokens در یک منبع واحد.
- Storybook یا ابزار مشابه فقط اگر با stack موجود سازگار است و به مستندسازی/QA ارزش می‌دهد.
- نمونه‌ها و component states برای اجزای پیچیده.
- هر استثنا باید rationale داشته باشد؛ صفحه‌ای که خارج از سیستم طراحی است باید دلیل مشخصی داشته باشد.
