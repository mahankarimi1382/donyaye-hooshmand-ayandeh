# QA، دسترس‌پذیری و معیارهای پذیرش

## 1. ماتریس viewport
حداقل این اندازه‌ها را بررسی کن (مقادیر به‌عنوان smoke-test هستند؛ breakpoint نهایی از محتوا تعیین می‌شود):
- 320×568 یا نزدیک آن: موبایل کوچک
- 360×800: موبایل رایج
- 390×844: موبایل بزرگ
- 768×1024: تبلت portrait
- 1024×768: تبلت landscape/نمایشگر کوچک
- 1366×768: دسکتاپ رایج
- 1440×900 یا بالاتر: دسکتاپ بزرگ

در هر اندازه: overflow افقی، navigation، تصویر، فرم، جدول، CTA، footer و spacing را مرور کن.

## 2. معیارهای پذیرش UX/UI
- [ ] تمام صفحات مهم با یک Design System منسجم طراحی شده‌اند.
- [ ] hierarchy تیتر، متن، بخش‌ها و CTA در هر صفحه روشن است.
- [ ] محصولات از مسیر واضح قابل یافتن‌اند.
- [ ] جزئیات محصول فقط داده واقعی را نمایش می‌دهد.
- [ ] CTA به مسیر واقعی می‌رود و نام آن عمل را توضیح می‌دهد.
- [ ] فرم‌ها validation و حالت‌های submit/success/error واقعی دارند.
- [ ] هیچ `href="#"`، دکمه خالی یا لینک دانلود خراب باقی نمانده است.
- [ ] صفحه 404 و empty/error state مسیر بازگشت دارند.
- [ ] RTL در همه اجزای اساسی شامل menu، form، table، modal، icon و pagination تست شده است.
- [ ] زبان دوم در صورت وجود، LTR/RTL و routeهای مستقل را حفظ می‌کند.
- [ ] تصاویر alt/ابعاد صحیح دارند؛ تصویر محتوایی مهم صرفاً با CSS background پوشش داده نشده است.

## 3. Accessibility
هدف پیشنهادی WCAG 2.2 AA است، اما conformant بودن باید با آزمون واقعی و تخصصی ارزیابی شود.
- [ ] ساختار heading بدون پرش منطقی و landmarkهای معنایی
- [ ] همه عملکردها با کیبورد قابل استفاده‌اند.
- [ ] focus visible است و به‌خاطر header/sticky element پوشانده نمی‌شود.
- [ ] ترتیب focus با ترتیب بصری و وظیفه کاربر سازگار است.
- [ ] inputها label واقعی دارند؛ placeholder جایگزین label نیست.
- [ ] error text با فیلد مرتبط است و برای screen reader قابل اعلام است.
- [ ] contrast متن معمولی حداقل 4.5:1 و متن بزرگ حداقل 3:1 هدف‌گذاری و تست شده است.
- [ ] رنگ به تنهایی state یا خطا را مشخص نمی‌کند.
- [ ] targetهای لمس در موبایل به‌اندازه کافی بزرگ و از هم جدا هستند؛ معیار پیشنهادی 44×44 CSS px برای عناصر اصلی.
- [ ] `prefers-reduced-motion` رعایت می‌شود.
- [ ] تصاویر تزئینی alt خالی و تصاویر اطلاعاتی alt معنی‌دار دارند.
- [ ] modal/drawer focus را مدیریت و پس از بسته شدن بازمی‌گرداند.
- [ ] zoom و تغییر اندازه فونت محتوای اصلی را غیرقابل استفاده نمی‌کند.
- [ ] بررسی اتوماتیک axe/Lighthouse به‌همراه مرور دستی انجام شده است.

## 4. تست‌های عملکرد
### Smoke test
- ورود به خانه و بازکردن تمام لینک‌های ناوبری
- ورود مستقیم به URL صفحه دسته و محصول با refresh
- جست‌وجو با نتیجه و بدون نتیجه
- فیلتر، پاک کردن فیلتر و back/forward
- ارسال فرم با داده معتبر، داده نامعتبر، خطای شبکه و ارسال تکراری
- دانلود سند واقعی یا مدیریت نبود سند
- باز/بسته کردن منو، dialog، accordion و dropdown با keyboard
- 404 برای slug نامعتبر

### Automated tests
- component/unit tests برای validation و state transitions
- E2E برای journeys حیاتی با Playwright یا ابزار موجود پروژه
- accessibility smoke test در چند route کلیدی
- تست responsive screenshots در صورت زیرساخت مناسب
- API contract tests در صورت وجود و فقط در scope مجاز

## 5. Technical checks
- [ ] lint موفق یا خطاهای baseline با موارد جدید تفکیک شده‌اند.
- [ ] typecheck موفق یا خطاهای baseline ثبت و علت آن‌ها روشن است.
- [ ] تست‌ها اجرا شده و نتیجه واقعی گزارش شده است.
- [ ] production build اجرا شده است.
- [ ] خطای runtime/console در مسیرهای کلیدی وجود ندارد.
- [ ] درخواست‌های شبکه شکست‌خورده توجیه نشده باقی نمانده‌اند.
- [ ] تصاویر و فونت‌ها بهینه و اندازه‌شان مشخص است.
- [ ] dependency جدید از نظر سازگاری، license، نگهداری و bundle بررسی شده است.
- [ ] secrets و payload حساس در client bundle/logs قرار ندارند.
- [ ] هیچ فایل user change پاک نشده است.

## 6. SEO و performance
- [ ] title/description متمایز برای routeهای مهم
- [ ] canonical/robots/sitemap طبق stack موجود
- [ ] redirect برای slugهای تغییرکرده در صورت نیاز
- [ ] تصاویر دارای dimensions و responsive source
- [ ] فونت‌ها و critical CSS بارگذاری کنترل‌شده دارند.
- [ ] بخش‌های heavy فقط در صورت نیاز load می‌شوند.
- [ ] معیارهای Core Web Vitals/Lighthouse قبل و بعد در محیط مشابه ثبت شده‌اند.
- [ ] structured data فقط بر اساس محتوای معتبر و نوع entity صحیح تولید می‌شود.

## 7. معیار پیشنهادی performance
از اهداف زیر به‌عنوان نقطه آغاز استفاده کن، نه تضمین خودکار:
- LCP حدود 2.5 ثانیه یا کمتر
- INP حدود 200 میلی‌ثانیه یا کمتر
- CLS حدود 0.1 یا کمتر
این اعداد باید با داده واقعی (ترجیحاً field data در صورت موجود بودن) و شرایط تست یکسان تفسیر شوند. Lighthouse score به‌تنهایی کیفیت UX را ثابت نمی‌کند.

## 8. نمونه گیت نهایی
**قبول:** مسیرهای اصلی کار می‌کنند، هیچ blocker شناخته‌شده وجود ندارد، صفحه‌های کلیدی responsive و RTL هستند، فرم‌ها واقعی‌اند، build و تست‌ها نتیجه مستند دارند.  
**رد:** فقط Home تغییر کرده، routeهای دیگر سبک قدیمی دارند، CTAها بی‌اثرند، فرم موفقیت جعلی نشان می‌دهد، محتوا/مجوز ساختگی است، تست انجام نشده یا گزارش بدون شواهد ادعای سبز بودن دارد.
