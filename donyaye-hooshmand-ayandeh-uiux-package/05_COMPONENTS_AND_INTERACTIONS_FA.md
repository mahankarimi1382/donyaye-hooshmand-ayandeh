# مشخصات کامپوننت‌ها، رفتارها و وضعیت‌ها

## 1. Header / Navigation
**باید:** لوگوی واقعی یا placeholder در محیط توسعه، navigation بر اساس sitemap، active route، CTA تماس/استعلام، mobile drawer/menu و مدیریت focus.  
**حالت‌ها:** default، hover، focus، active route، expanded/collapsed، scrolling/sticky در صورت نیاز.  
**تست:** keyboard، Escape برای بستن، بازگرداندن focus، عدم پوشش محتوای اصلی، RTL و عرض کم.

## 2. Hero
**باید:** تیتر قابل فهم، توضیح مختصر، CTA اصلی، CTA ثانویه اختیاری، تصویر مرتبط و مجاز.  
**نباید:** اسلایدر خودکار به‌عنوان پیش‌فرض، متن غیرقابل راستی‌آزمایی، سه CTA هم‌وزن یا تصویر stock که به‌عنوان کارخانه شرکت تلقی شود.

## 3. Product card
- تصویر با aspect ratio پایدار و alt
- نام محصول واقعی
- توضیح کوتاه با محدودیت طول
- یک یا دو ویژگی کلیدی فقط وقتی داده‌شان معتبر است
- لینک جزئیات واضح
- CTA استعلام اختیاری با product context
- حالت تصویر ناموجود و نام خیلی بلند
- کل کارت و لینک‌های تو در تو نباید nested interactive elements نامعتبر بسازند.

## 4. Category card
نام دسته، توضیح کوتاه/تعداد محصول فقط اگر شمارش داده صحیح است، و مسیر واقعی. آیکون تزئینی نباید جای نام قابل فهم را بگیرد.

## 5. Product specification table
- دو ستون label/value روی دسکتاپ؛ در موبایل تبدیل به layout خوانا یا جدول قابل پیمایش کنترل‌شده
- نام، مقدار، واحد و توضیح آزمون در صورت لزوم
- فیلد خالی از UI عمومی پنهان شود یا به‌روشنی «اعلام نشده» نشان داده شود؛ صفر فرض نشود
- برای اعداد با واحد یکپارچه و ترجیحاً tabular numeral
- کپی/انتخاب متن و دسترس‌پذیری حفظ شود.

## 6. Search / Filter / Sort
- label یا accessible name واضح
- Enter برای جست‌وجو، Escape برای پاک‌سازی/بستن dropdown طبق الگوی کتابخانه
- وضعیت pending/loading
- حفظ query/facets هنگام back/forward اگر معماری اجازه می‌دهد
- دکمه پاک کردن فیلترها
- empty state با توضیح و reset
- فیلترهای بدون داده یا بدون منبع واقعیت نمایش داده نشوند.

## 7. فرم استعلام
**فیلدهای احتمالی، مطابق نیاز واقعی و با حداقل‌سازی:** نام، سازمان/شرکت در صورت نیاز، کانال تماس ترجیحی، ایمیل یا تلفن (الزام لازم به شکل روشن)، محصول، مقدار/بازه تخمینی در صورت نیاز، زمان/مقصد تحویل اگر برای فرآیند فروش لازم است، پیام اختیاری. فیلدها را بر اساس قرارداد API/CRM و privacy تعیین کن، نه فهرست پیشنهادی را کورکورانه اجرا کن.

**رفتار لازم:**
1. label قابل مشاهده و placeholder صرفاً کمکی.
2. validation با زبان واضح و بدون پاک‌کردن داده واردشده.
3. `aria-invalid` و اتصال خطا به فیلد.
4. ارسال با Enter فقط در الگوی معتبر فرم و بدون ارسال ناخواسته در multiline.
5. جلوگیری از ارسال چندباره، نمایش وضعیت pending.
6. موفقیت فقط بعد از پاسخ معتبر سیستم مقصد.
7. خطای شبکه/سرور با حفظ اطلاعات فرم و راه جایگزین تماس.
8. پیام privacy مطابق سیاست واقعی، بدون وعده حقوقی نادرست.
9. ضداسپم و rate-limit در سمت backend یا سرویس مناسب؛ فقط front-end کافی نیست.
10. ثبت analytics بدون ثبت محتوای شخصی کاربر.

## 8. Contact section / Contact page
- نمایش فقط کانال‌های رسمی تأییدشده
- شماره تماس با `tel:` و ایمیل با `mailto:` در صورت مناسب بودن
- نشانی، ساعت کاری، شبکه اجتماعی و نقشه فقط در صورت داده معتبر
- روش دسترسی جایگزین در خطای فرم
- در موبایل شماره/CTA قابل tap باشد.

## 9. Buttons & Links
- دکمه برای action و لینک برای navigation.
- label با فعل و نتیجه مشخص: «مشاهده مشخصات»، «ارسال درخواست»، «دانلود برگه فنی».
- بدون `href="#"` یا کنترل بی‌عمل.
- disabled فقط برای حالتی که علت قابل فهم و در صورت امکان راه رفع دارد.
- یک CTA اصلی در هر بخش؛ hierarchy روشن.

## 10. Dialog / Drawer / Dropdown / Accordion
- keyboard support، focus trap برای modal، Escape و بستن با control واضح
- باز/بسته شدن با `aria-expanded` یا semantics کتابخانه
- focus پس از close به trigger برگردد
- محتوا نباید با hover-only مخفی شود
- در موبایل پنل نباید از viewport بیرون بزند
- برای محتوای زیاد، modal کوچک را به صفحه کامل تبدیل کن.

## 11. Loading / Empty / Error / Success
- Loading: skeleton برای ساختارهای قابل پیش‌بینی؛ از spinner بی‌نهایت استفاده نکن.
- Empty: وضعیت توضیح دهد چرا چیزی نمایش داده نمی‌شود و چه کاری می‌توان کرد.
- Error: زبان انسانی، بدون افشای stack trace یا جزئیات حساس، retry در صورت امن بودن.
- Success: تأیید واقعی + نتیجه بعدی روشن، بدون وعده‌ای که کسب‌وکار تأیید نکرده باشد.
- Partial failure: بخشی از صفحه که سالم است باید در صورت امکان باقی بماند.

## 12. Toast / Alerts
- toast برای feedback کوتاه و غیرمسدودکننده؛ خطای مهم فرم باید کنار فیلد و در summary هم قابل یافتن باشد.
- رنگ تنها نشانگر state نیست.
- پیام باید به زبان کاربر و شامل اقدام پیشنهادی باشد.
- toast نباید آن‌قدر سریع محو شود که خواندنش دشوار باشد؛ پیام حیاتی پایدارتر ارائه شود.

## 13. Footer
- ساختار ستون‌ها بر اساس اولویت واقعی: شرکت، محصولات، اطلاعات تماس، منابع، سیاست‌ها.
- اطلاعات تماس و شبکه‌های اجتماعی بدون تأیید درج نشوند.
- لینک‌های شکسته و تکراری ممنوع.
- در موبایل از accordion فقط وقتی محتوا زیاد و کاربردش روشن است استفاده کن.

## 14. قراردادهای فنی
- type-safe props/data models
- مدیریت error boundary مطابق stack
- اجتناب از client state اضافی برای داده‌ای که server/router مدیریت می‌کند
- جلوگیری از state duplication بین URL، form و global state
- componentهای کوچک، اما نه تقسیم افراطی تا حد دشواری تغییر
- تست‌های component برای behavior، نه فقط snapshot کلاس CSS
